# Метод 2 указателей
Метод, который иногда можно использовать вместо бинарного поиска. Задачи, решаемые бинпоиском можно решить и таким способом, но не всегда есть пересечение этих методов.
Этот метод более быстрый, чем бинпоиск

В качестве указателей мы будем использовать индексы элементов массива, номера в какой-то последовательности, символы строки и тд. 

## Идея метода
Общая идея метода двух указателей заключается в следующем: 
Мы моделируем какой-то процесс, обрабатывающий элементы одного или двух массивов, при котором для каждого указателя задано направление, в котором он двигается. **В обратном направлении указатели не двигаются**

## Почему метод быстрый?
Для того, чтобы метод работал, необходимо условие, что каждый указатель движется только в одном направлении
Почему так? 
Предположим, что есть два указателя, один на массиве размера `n`, второй на массиве размера `m`.  И для каждого из этих указателей есть направлении, в обратном которому он не движется никогда. Мы можем показать, что суммарное количество действий по перемещению указателей и проверки элементов оценивается как $O(n+m)$. Каждое действие будет вызывать перемещение одного из двух указателей. Первый указатель может переместиться суммарно на `n` позиций, второй на `m` позиций. Как только начинается движение в обратном направлении, мы не можем сказать, что указатель совершит больше `n` перемещений (для массива размером `n`)

## Пример
Дан массив из n целых чисел, а также целое число k. Надо найти два элемента в массиве с суммой ровно k

```
arr = 3 8 4 5 2 1 4 3
k = 9
```

Можно решить задачу тупым способом, тогда время работы будет: 
$$
\left( \begin{array}l
n \\
2
\end{array} \right) = \frac{n(n-1)}{2} \to O(n^2)
$$

Суммарное время работы будет $O(n\log n)$ предварительной обработки + $O(n)$ время работы поиска. То есть суммарное время будет $O(n\log n)$. Но, может возникнуть ситуация, что нам нужно несколько разных проверок на одном массиве, тогда поиск отработает за $O(n)$. Если $q$ запросов к одному и тому же массиву, то получим время $O(n\log n)$ на обработку $O(qn)$ на поиск. То есть суммарное время работы $O(n\log n + qn)$

Допустим, мы посмотрели пару элементов $a_{i}$ и  $a_{j}$: 
$$
a_{i} \text{ и } a_{j} \qquad \left\{\begin{array}l
a_{i} + a_{j} = k \\
a_{i} + a_{j} < k  \\
a_{i} + a_{j} > k
\end{array} \right.
$$

если нам нужно больше, значит, что сумму надо увеличить если нужно меньше, значит, сумму нужно уменьшить 
```
i - увеличение
j - уменьшение
```

Значит, если нужно увеличить сумму, мы будем менять элемент i на элемент побольше. Если нужно уменьшить - j на элемент поменьше
И там и там замена на **максимально близкий по значению** к предыдущему

А как вообще поменять элемент на элемент больше? 

Допустим, i = 1. Как для этого элемента найти элемент больше? 
Из элементов данного массива нужно выбрать следующий по значению элемент

Если мы этот массив отсортируем
```
3 8 4 5 2 1 4 3 -> 1 2 3 3 4 4 5 8
```
Тогда, какой элемент мы бы ни посмотрели в виде i, то ближайший больший будет следующим элементов в массиве

## Другой пример
```
3 5 6 7 9 11 13 16
k = 13
```

поставим i = 3; j = 16
в сумме 19, двигаем элемент, который будет отвечать за уменьшение, тогда:
i = 3; j = 13 => sum = 16
i = 3; j = 11 => sum = 14
i = 3; j = 9 => sum = 12
i = 5; j = 9 => sum = 14
i = 5; j = 7 => sum = 12
i = 6; j = 7 => sum = 13 завершаем процесс

Докажем, что, если два указателя совпали, то в этом методе больше не нужно проверять элементы

Предположим, что есть два элемента с нужной суммой. Докажем, что мы не пропустим такие элементы
```
... x ... y ...
a[x] + a[y] = k
```

Если мы не нашли ответ, то это значит:
- i = j
- не было никогда ситуации, что i = x и одновременно j = y

докажем, что это невозможно, разберём два случая: 
Либо первым совпало i = x
Либо первым совпало j = y

Доказательство одинаково для обоих случаев. 

Предположим, что первым выполнилось i = x. Это означает, что i указывает ровно туда, куда нам нужно, а j пока что где-то правее, чем позиция y 

Как a\[i\] + a\[j\] соотносятся с k? 
Пусть a\[i\] + a\[j\] < k: невозможно, так как a\[j\] >= a\[y\], a\[i\] = a\[x\], a\[x\] + a\[y\] = k
либо a\[i\] + a\[j\] = k: нашли ответ
либо сумма < k, тогда уменьшим j на один элемент, тогда он через несколько раз попадёт в позицию y

Из этого следует, что текущая сумма не может быть меньше чем k, она либо больше, либо равна => решение гарантировано находит нужный ответ

```cpp
#include <iostream>
#include <vector>
#include <ctime>

using namespace std;

void preprocces(vector<int>& a) {
    sort(a.begin(), a.end());
}

bool sumOf2(const vector<int> &a, int k) {
    // в отсортированном массиве a проверяем
    // есть ли пара, a[i], a[j]:
    // i != j, a[i] + a[j] = k
    int n = a.size();
    int i = 0, j = n - 1;

    while (i != j) {
        int cur = a[i] + a[j];
        if (cur == k)
            return true;
        else if (cur < k)
            i++;
        else
            j--;
    }
    return false;
}

int main()
{
    cout << sumOf2({3, 5, 6, 7, 8, 11, 13, 16}, 13);
}
```

# Сортировка слиянием (Merge Sort)
Проблема quick sort в том, что если опорный элемент выбрался так, что этот элемент либо минимальный, либо максимальный, это приведёт к тому, что мы слишком глубоко уйдём в рекурсию, и будем расходовать слишком много памяти

Отличие Merge sort от quick sort. В Merge Sort массив будет делиться на две части максимально близкого размера. Это сразу убирает проблему того, что разбиение может работать не за одинаковое время

## Общая схема
```pseudocode
MergeSort(a):
	if |a| <= 1:
		return a
	else:
		al = левая половина a
		ar = правая половина a
		al' = MergeSort(al)
		ar' = MergeSort(ar)
		return Merge(al', ar')
```

минус по сравнению с quick sort - больший расход памяти и по времени работы обычно хуже чем quick sort
плюсы по сравнению с quick sort - нет худшего случая в виде $O(n^2)$ и этот алгоритм сортировки устойчивый - то есть порядок одинаковых элементов сохранится

## Слияние
мы будем использовать метод слияния, который будет работать следующим образом: 

```
1 3 3 7
2 4 4 6
```

первый элемент результата будет всегда первый элемент из первого или второго массива

зададим два указателя i, j, каждый из этих указателей будет указывать на первый необработанный элемент первого и второго массива соответственно


```cpp
#include <ctime>
#include <iostream>
#include <vector>

using namespace std;

vector<int> merge(vector<int> &a, vector<int> &b) {
  int i = 0;
  int j = 0;
  int n = a.size();
  int m = b.size();

  vector<int> c(n + m);

  // 1 фаза:
  // не дошли до конца ни в одном из массивов
  while (i < n && j < m) {
    if (a[i] <= b[j]) {
      c[i + j] = a[i];
      i++;
    } else {
      c[i + j] = b[j];
      j++;
    }
  }

  // 2 фаза:
  // доходим до конца другого массива
  while (i < n) {
    c[i + j] = a[i];
    i++;
  }

  while (j < m) {
    c[i + j] = b[j];
    j++;
  }
}

vector<int> mergeSort(vector<int> &a) {
  int n = a.size();
  if (n <= 1)
    return a;
  else {
    vector<int> al = vector<int>(a.begin(), a.begin() + n / 2);
    vector<int> ar = vector<int>(a.begin() + n / 2, a.end());
    al = mergeSort(al);
    ar = mergeSort(ar);
    return merge(al, ar);
  }
}

int main() {}
```

```python
def merge(a, b):
    i = 0
    j = 0
    n = len(a)
    m = len(b)
    c = [0 for i in range(n + m)]

    while i < n and j < m:
        if a[i] <= b[j]:
            c[i + j] = a[i]
            i += 1
        else:
            c[i + j] = b[j]
            j += 1

    while i < n:
        c[i + j] = a[i]
        i += 1

    while j < m:
        c[i + j] = b[j]
        j += 1


def mergesort(a):
    n = len(a)
    if len(a) <= 1:
        return a
    else:
        al = mergesort(a[: n // 2])
        ar = mergesort(a[n // 2 :])
        return merge(al, ar)

```

Работает за $O(n\log n)$. Почему? Потому что сам merge работает за $O(n+m)$ откуда берётся логарифм в сортировке? Если рассмотреть дерево рекурсивных вызовов, на каждом уровне рекурсии тратится $O(n)$ времени на разбиение и столько же на слияние. А глубина рекурсии будет гарантировано $O(n\log n)$
